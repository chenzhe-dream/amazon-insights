# Alexa 真实七问报告兼容性设计

**日期：** 2026-08-30

**状态：** 已确认

**适用工作流：** 登录后的“Alexa 七问 · 快速录入”、`npm run alexa:import` 与自动抓取后的同一写入管线。

## 目标

业务人员使用下列七问模板向 Alexa for Shopping 提问后，应可将 Alexa 的**完整原始回答**直接粘贴导入，不必手工替换标题、补全分隔符或整理表格：

> 这个产品的顾客关注点是什么，好评点是什么，差评点是什么，未被满足的需求是什么，使用人群是谁，使用场景是什么，核心购买动机是什么。

系统采用确定性的多格式解析与规范化：真实回答中的七个维度均被识别并归入现有 `rufus-voc-data.ts` 七维矩阵；一个脱敏的真实格式回归样本必须得到 `7/7`。好评率、差评率、提及次数、星级、未知值等指标必须保留其原始语义，不能伪造为另一种指标。

## 非目标

- 不调用 LLM、第三方 API 或 Alexa 之外的服务来二次理解、补全或改写报告。
- 不从“综合结论”或无标题散文中推断七维，不以降低门槛的方式把猜测写入 VOC。
- 不改变 Amazon 登录、浏览器抓取、鉴权、原子写入、Artifact 发布和重载协议。
- 不把用户提供的完整原始业务报告、品牌、真实 ASIN、报价或评论原文提交到仓库；测试只保存脱敏且结构等价的 fixture。
- 不修改七维的业务定义或将父体数据替代子 ASIN 数据。

## 现状与根因

`scripts/lib/parse-alexa-voc-report.mjs` 目前只识别少量“序号 + 特定 emoji + 全角括号”标题，如 `1️⃣ 顾客关注点` 和 `✅ 2. 好评点`。真实 Alexa 输出会使用无序号标题，例如 `🎯 顾客关注点 (客户最在乎什么)`、`✅ 好评点 (为什么给好评)`，并可使用 ASCII 或全角括号。复制到文本框后，表格还可能退化为逐行单元格，而非 `｜` 或 Tab 行。

因此，真实报告虽然具备七个标题，现有 `sectionStarts` 仍可能为空，最后触发 `incomplete_report`。问题不是 600 字限制、ASIN、鉴权或后台发布；已有的“非空即可提交”规则应继续保留。

## 输入合同

### 基本合同

1. 输入是 UTF-8 纯文本，保留既有上限：128 KiB、1,000 行、单行 2,048 字符、表格最多 256 行；空白输入仍为 400。
2. 首部或全文中必须有一个 10 位 ASIN；其规范化大写值必须等于下拉选择的 ASIN。任何不匹配在写缓存、投影、快照、状态或发起发布前以 422 拒绝。
3. 七维以实际解析并规范化后的非空结果计数；低于 3 维仍拒绝。`processAlexaVocText().ok` 的较强质量信号（至少 5 维且含好评/差评）可继续用于调用方状态，但不得替代保存的 3 维安全门槛。
4. 同一报告可同时含标题、普通段落、纵向表格、Markdown 表格、编号分行和总结；解析结果必须只来自所属维度的边界内。

### 标题识别

七个标准标题及内部 key 固定如下：

| 标准标题 | key |
| --- | --- |
| 顾客关注点 | `attention` |
| 好评点 | `positives` |
| 差评点 | `negatives` |
| 未被满足的需求 | `unmet` |
| 使用人群 | `audiences` |
| 使用场景 | `scenarios` |
| 核心购买动机 | `motives` |

标题匹配必须以“去除前导空白、可选 Markdown 标记、可选 emoji、可选 `#`、可选阿拉伯/键帽数字及分隔符”后的**行首标准标题**为锚点。标准标题之后允许：

- 空白；
- `:`、`：`、`-`、`—`；
- ASCII `(...)` 或全角 `（...）` 的说明文字；
- 标题同义短尾 `购买动机`（仅映射到 `motives`）、`未被满足`（仅映射到 `unmet`）。

因此下列均须识别：`🎯 顾客关注点 (客户最在乎什么)`、`✅ 好评点（为什么给好评）`、`❌ 3. 差评点`、`7️⃣ 核心购买动机`、`## 使用场景：`。匹配不得依赖某一个 emoji、序号或括号种类。

标题匹配不得把正文中的“顾客关注点是什么”“好评点包括”或表格单元格误当标题：除标准标题外，行上不得有其它实质性前缀；括号外的尾部文本仅能是上述允许的分隔或说明。`综合结论`、`购买决策链`、`最核心的五大购买理由` 是总结/附录标题，不是七维，绝不计数。

## 分段边界

解析器先对全部行做换行与空白规范化，再一次性收集七维标题的位置；按文档出现顺序排序。每个维度的原料为“本标题下一行至下一已识别七维标题的前一行”。

在没有下一个七维标题时，遇到 `综合结论`、`总体结论`、`Conditions of Use`、版权/来源尾注或文末即停止；这些总结行只可供既有 `overallConclusion` 提取，不得回流到前一维度。此规则保证“购买决策链”若位于购买动机段中会作为该段正文保留，而“综合结论”不会污染动机。

若某标准标题重复出现，第一次标题到下一标题为一个块；同 key 的后续块按文档顺序追加并去除完全相同的规范化行。不同维度不得跨块拼接。

## 三种结构的确定性解析

实现应在 `parse-alexa-voc-report.mjs` 中将每一节解析为带结构的中间行/记录，再由 `normalize-alexa-voc-sections.mjs` 生成现有字符串数组。不得通过全局正则跨段寻找项目。

### 1. 保持列的表格

支持 Tab、全角竖线 `｜` 和 Markdown ASCII 竖线 `|`。对 Markdown 行，去掉可选首尾竖线，按 `|` 切分并 trim；仅由 `-`、`:`、空白组成的对齐行丢弃。输出统一使用 `｜`。

表头由顺序列名识别，不按固定字面全等：

- 关注点：排序/序号、关注点、提及次数/数据、为什么重要/说明；
- 好评点：特性/好评点、好评率/正向比例、核心评价、典型评论；
- 差评点：问题/差评点、差评率/负向比例、投诉内容、受影响群体；
- 人群：人群分类/身份、特征/需求/购买动机；
- 场景：场景、使用率/重要性、典型用法/说明、用户类型；
- 动机：动机/驱动力、重要性、说明/依据。

只要一行的有效列数不少于该维度最低列数，就保留该行；缺失单元格写为空字符串，不与下一行借位。人群、场景、动机的输出仍含既有系统表头，例如 `人群分类｜特征`、`场景｜说明与示例`、`动机｜重要性｜说明`。

### 2. 纵向复制表格

某些浏览器复制会把一个视觉表格变为“表头各占一行，随后每个单元格各占一行”。在单一 section 内，发现上述完整列序列后，按该表头列数将随后连续的非标题、非编号正文单元格分组为记录。只接受完整组；尾部不足一组的单元格转回普通段落，不得移入上一条记录。

组装规则固定且可审计：

- `attention`：`#序号 + 关注点 + 提及次数 + 原因` 生成一个编号关注项，保留“136次”“79条Q&A”等原词；
- `positives`：`特性 + 好评率 + 核心评价 + 典型评论` 生成 `【特性】好评率 <原值> · <核心评价> · <典型评论>`；
- `negatives`：`问题 + 差评率 + 投诉内容 + 受影响群体` 生成 `【问题】差评率 <原值> · <投诉内容> · <受影响群体>`；
- `audiences`、`scenarios`、`motives`：以各自列顺序折叠为规范 `｜` 行，缺失值保持空列。

这是一种结构转换，不解释产品事实。`部分`、`不详`、星级符号、英文值、Q&A、百分号和原有引号必须原样保留。

### 3. 编号与正文分行

支持 `1.`、`1、`、`1)`、`#1`、`🔴 #1` 以及仅含编号的行。仅含编号的行将与其紧随的第一个非空文本行组成项目标题。该项目后直到下一个同层编号、表头或 section 边界的 `•`/`-` 子项视为该项目说明，并以 ` · ` 追加；普通续行以空格续接。空编号、孤立符号或无正文的项目不计入维度。

应用方式：

- `attention` 与 `unmet` 生成编号列表。`未被满足的需求`中的“现状”“需求”“对标”作为该需求的说明，不成为新需求。
- `audiences` 与 `scenarios` 的编号项目变为一条 `｜` 表格记录；编号标题为第一列，子项字段合并到第二列。
- `motives` 的编号驱动力变为 `动机｜重要性｜说明` 记录。若标题或子项中含 1–5 个 `★`/`⭐`，保留为重要性；无星级时第二列为空，不能凭编号推定五星。
- `positives` 与 `negatives` 的非表格编号项目保留标签及连续说明，不能要求其必须有“次数 + 百分比”的旧模式。

解析优先级是“保持列的表格”→“纵向复制表格”→“编号/正文分行”→“安全的普通段落”。一段已被前一规则消费的行不能被后一规则再次生成条目；最终按首见顺序去重。

## 指标语义与规范化

当前 `normalizePositives`/`normalizeNegatives` 会偏向 `约 X% 评论提及（N 条）`。新实现必须区分来源词，禁止凭看起来相近而转换：

| 输入原词 | 保存语义 |
| --- | --- |
| `136次`、`136 次提及`、`79条Q&A` | 提及次数或 Q&A 条数，保留原文本；仅当原文同时明确给出评论总数且来源确为评论提及时，才可附加可复算的评论提及占比。 |
| `83% ⭐⭐⭐⭐⭐`、`好评率 83%` | 好评率；不得写成“83% 评论提及”。 |
| `差评率 6%` | 差评率；不得写成“6% 评论提及”。 |
| `部分`、`不详` | 未知/非量化值，原样保留，不补零、不计算百分比。 |
| Markdown 的 `⭐`/`★` | 重要性/评价星级符号；在动机第二列时统一为既有黄色星形展示，但数量不变。 |

既有旧格式 `质量可靠（好评维度10次提及，20%）`、`包装有待改善（差评维度5次提及，10%）` 仍按原有规则生成标准化 `评论提及` 文本。新格式的 `好评率`、`差评率`则走独立格式化函数，显式标注为对应比率。不得用 catalog 评论数重算或覆盖 Alexa 已给出的好/差评率。

`reviewCount`、`rating`、`starBreakdown` 的首部抽取保持兼容；首部为“产品名 (ASIN) — 完整顾客行为分析”也必须识别 ASIN，不能只接受“顾客洞察完整分析”。若原文无评论数，允许使用既有 catalog 的评论总数作为**报告元数据回退**，但不得据此把好评率/差评率改名或改值。

## 数据流与写入安全

```text
原始文本
  -> 限额校验
  -> 标题扫描 + section boundaries
  -> 各 section 的确定性结构解析
  -> 指标语义保真的七维规范化
  -> ASIN 一致性 + 至少 3 个非空维度
  -> 原子提交 cache / rufus-voc-data / publication state
  -> 既有后台 Artifact 发布请求
```

`saveAlexaVocToSystem` 必须在任何 `commitAlexaVocUpdateSync` 调用前完成 ASIN、限额、解析与“至少三维”检查。发生结构/ASIN/完整度错误时，缓存文件、`app/rufus-voc-data.ts`、快照和 publication state 均不得变化。原始报告仍只进入既有每 ASIN cache，不被放入 HTTP 错误、浏览器日志或 UI 提示。

鉴权仍先于读取请求体；同源与角色策略不变。该兼容功能只处理用户已经提交的本地文本，不创建浏览器会话、不访问 Amazon、不启动服务端口，也不引入网络依赖。

## 错误、诊断与 UI

后端对“已成功读取但少于三维”的 422 响应必须保留稳定前缀：

```text
Alexa 报告至少需要识别 3 个维度；检测到：顾客关注点、好评点；缺失：差评点、未被满足的需求、使用人群、使用场景、核心购买动机
```

`检测到`来自标题扫描，`缺失`来自规范化后的空维度；若标题存在但内容无法形成有效条目，该维度必须列入缺失，并可在该维度名后标注“内容未形成有效条目”。错误中不得回显报告全文、Cookie、Token、内部路径、密钥或未脱敏评论。

成功响应继续包含 `filled`、`missing`、三维预览和发布状态；可新增仅含标准维度名的 `detected` / `invalid` 字段供 UI 显示。`AlexaVocImportPanel` 的提示改为“可直接粘贴 Alexa 完整回复；支持无序号标题、ASCII/全角括号与复制表格”，placeholder 不再暗示唯一的“顾客洞察完整分析”首部。前端无需自行解析，仍以服务端结果为准。

## 向后兼容

- 保留原有 `1️⃣–7️⃣`、`📌 1.`、`✅ 2.`、`❌ 3.`、`💬 4.`、`👨‍👩‍👧‍👦 5.`、`🎯 6.`、`🛒 7.` 标题。
- 保留全角 `｜`、Tab 表格、原来的编号列表、现有 `overallConclusion` 和生成文件接口。
- 保留 `parseAlexaVocReport(rawText, asinHint)`、`normalizeAlexaVocSections(sections, options)`、`processAlexaVocText`、`saveAlexaVocToSystem` 的调用方式；可增加显式诊断字段，但不得移除现有字段。
- 不改变旧报告的可导入性、ASIN 零写入不匹配保护或任何发布顺序。

## 测试与验收

### 脱敏 fixture

fixture 使用虚构品牌与测试 ASIN（例如 `B0ALEXA001`），替换真实商品名称、价格、评论原话和可识别业务数值；但必须保留以下格式特征：

1. 无序号 emoji 七标题，混用 ASCII 与全角括号；
2. `attention`、`positives`、`negatives` 的纵向复制表格；
3. 至少一张带半角 `|`、首尾竖线和对齐行的 Markdown 表格；
4. `unmet`、`audiences`、`scenarios`、`motives` 的“编号单独一行 + 正文 + 子项”结构；
5. 真实语义不同的 `提及次数`、`好评率`、`差评率`、`部分`/`不详`、星级；
6. 一个不计数的 `综合结论`。

### 必须通过的断言

1. `parseAlexaVocReport(fixture)` 识别 ASIN 和全部七个标准标题；每个 section 有至少一个有效原料记录，`missing` 为空。
2. `processAlexaVocText(fixture, fixtureAsin)` 得到 `filled === 7`、`missing === []`，并保持 `ok === true`。
3. 关键保真断言至少包括：一个原始 `136次`/等价提及值仍是次数、一个 `好评率 83%`/等价值仍标注好评率、一个 `差评率 6%`/等价值仍标注差评率、一个 `部分`或`不详`仍存在、一个 Markdown 行被转为 `｜`、一个分行编号需求没有丢失其“现状/需求”说明。
4. 关注点/好评/差评的列不得错位：首列标签只能与其同组指标、评价/投诉、受影响群体结合；尾部残缺列不生成记录。
5. `综合结论`不增加 `filled`，也不出现在动机最后一条。
6. 现有 `reportFor()` 旧格式和已有 `rufus-voc-data.ts` 格式化输出继续通过；至少验证旧格式 3 维可写入、ASIN 不匹配零写入、长度阈值未恢复。
7. 导入路由对少于三维的报告返回 422，正文同时含稳定前缀、检测到的标题名和缺失维度名；错误不含输入原文或注入的密钥 sentinel。
8. 真实格式 fixture 经临时 worktree 的 `saveAlexaVocToSystem` 后，cache 原文等于 fixture、生成投影含 7 维关键值；不得启动真实构建、实际服务、浏览器或外部网络。

## 实施判定

只有当上述 fixture 和旧格式都通过、指标未被误称、低于三维仍安全拒绝、错误可诊断且无敏感回显时，本兼容性改动才可进入人工 VSCode 粘贴测试。人工测试的输入应使用实际 Alexa 完整回答；成功后页面应显示“已识别 7 / 7 维”并沿用既有后台正式页面发布流程。
