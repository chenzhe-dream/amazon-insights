# 20 人并发与卖家精灵额度管理设计

日期：2026-08-22
状态：已由用户确认设计方向，等待书面规格复核

## 1. 背景

系统需要支持最坏情况下约 20 名用户同时提交完整的 3-ASIN 分析。这里的“支持并发”不等于同时向所有外部 MCP 和模型发出 20 组请求，而是：

1. 20 个提交请求均可快速、可靠地被接收；
2. 任务持久化排队，页面刷新、重新登录或服务重启后仍可恢复；
3. 后台按受控上限执行，避免卖家精灵、SIF、Sorftime、图片分析和模型被瞬时流量击穿；
4. 相同市场与 ASIN 范围的任务复用，不重复消耗额度；
5. 管理员可看到卖家精灵额度和队列状态，最高管理员可调整执行策略。

卖家精灵官方说明：API 和 MCP 均按实际 HTTP 请求次数计数；一次用户提交可能产生多次 MCP 请求。官方提供 `GET /v1/visits` 查询当前月份可用次数，并标注每分钟 40 次的限制。本系统不得把“用户点击次数”当成卖家精灵实际消耗。

## 2. 目标与非目标

### 2.1 目标

- 接受 20 名用户同时提交完整分析。
- PostgreSQL 成为任务身份、排队、租约、状态与额度快照的唯一持久化事实源。
- 标准档最多同时执行 4 个完整任务，其余任务公平排队。
- 分别限制每个外部连接器、图片分析与模型调用的并发和速率。
- 卖家精灵额度不足、限流或熔断时，任务进入明确的等待状态，不停留在虚假的 96%。
- 所有并发策略调整有权限控制和审计记录。
- 系统只自动降级，不自动升档。

### 2.2 非目标

- 本阶段不直接部署多台服务器或 Kubernetes。
- 不保证 20 个完整分析同时完成；保证的是可靠接收、排队、公平执行和可恢复。
- 不猜测卖家精灵套餐总额度；官方响应不包含总额时，由最高管理员配置已购买总额。
- 不因扩并发而放宽现有租户隔离、认证、预算、任务租约或输出验证。
- 不在容量测试中同时触发 20 个真实付费任务。

## 3. 方案选择

### 3.1 已选方案

采用“PostgreSQL 持久队列 + 单机受控并发 + 未来可横向扩展 Worker”。

请求链路：

```text
20 名用户同时提交
        ↓
认证、组织校验、每用户准入
        ↓
PostgreSQL 创建任务或返回去重命中的任务
        ↓
公平调度器按用户轮转领取任务
        ↓
最多 N 个完整任务同时执行
        ↓
每个连接器再经过自己的信号量和速率限制
        ↓
状态、报告、额度快照持续写入 PostgreSQL
```

### 3.2 未选方案

- 20 个任务直接并行：容易触发供应商限流、费用失控和资源雪崩。
- 立即上多台 Worker：扩展性更强，但本地交付阶段增加部署复杂度。现有 PostgreSQL 租约边界应保留，使后续可无损增加 Worker。

## 4. 持久队列与任务身份

### 4.1 任务事实源

同步编排任务应持久化到 PostgreSQL，不再依赖仅存在于本机文件系统的 JSON 作为并发协调事实源。文件可继续作为脱敏诊断日志，但不得用于决定任务所有权或并发名额。

任务至少包含：

- `organization_id`
- `created_by_user_id`
- `project_id`
- `run_id`
- `marketplace`
- 规范化 ASIN 集合
- 去重指纹
- `queued | running | completed | completed-with-gaps | failed | paused`
- 当前阶段、逐 ASIN 状态、排队时间、开始时间、完成时间
- lease owner、generation、到期时间
- 策略快照版本

### 4.2 去重

相同组织、市场、规范化 ASIN 集合和数据有效期内的活动任务只能有一个。并发提交者获得同一个 `jobId`，不得启动第二个 Worker。

`runId` 保留为审计和报告关联，但不应破坏同一业务范围的活动任务去重。

### 4.3 公平性

调度器按用户轮转领取任务，避免单个用户连续提交占满全部运行名额。

- 单用户最多 1 个运行任务；
- 单用户最多 2 个排队任务；
- 超出限制时返回现有任务或明确的准入错误；
- 组织队列默认容量 100，达到上限后拒绝新增任务，但不影响读取已有任务。

## 5. 并发策略

### 5.1 三档策略

| 策略 | 完整任务 | 卖家精灵 | 其他 MCP | 模型调用 | 图片分析 |
|---|---:|---:|---:|---:|---:|
| 保守 | 2 | 1 | 各 1 | 1 | 全局 2 |
| 标准 | 4 | 2 | 各 1 | 2 | 全局 2 |
| 高速 | 6 | 3 | 各 2 | 3 | 全局 2 |

默认使用“标准”。“高速”只有在 fake-provider 容量测试和小规模真实阶梯验证通过后才允许启用。

卖家精灵无论选择哪个档位，本系统速率上限均不得超过每分钟 30 个实际 HTTP 请求，为官方每分钟 40 次限制预留查询、重试和时钟误差空间。

### 5.2 应用规则

- 20 个提交均可进入持久队列，但只有策略允许的任务数进入 `running`。
- 策略修改只影响后续 claim 和尚未开始的外部调用，不强杀正在执行的调用。
- 图片并发是全局 2，不是“每个任务 2”。
- 每个连接器使用独立全局信号量；不得在每个任务中各建一份限流器。
- 重试同样消耗连接器速率和额度，必须经过同一限流器。
- PostgreSQL 连接池初始显式限制为单进程最多 10 个连接，容量测试后再调整。

## 6. 卖家精灵额度

### 6.1 权威数据与本地计数

系统每 30 至 60 分钟调用一次卖家精灵 `GET /v1/visits`，并在管理员手动刷新时允许额外调用一次。不得在每个业务请求前查询额度。

系统保存：

- 当前月份剩余次数；
- 套餐总次数，可空；
- 已使用次数，可在总额已知时计算；
- 本系统当月实际发出的卖家精灵 HTTP 请求数；
- 最近成功查询时间；
- 数据来源：`provider | configured | local-observed`；
- 最近的限流或额度错误。

如果官方响应不含套餐总额，最高管理员可配置购买总额。未配置时 UI 显示“总额度未知”，只展示官方剩余量和本系统观察到的消耗，不推算虚假百分比。

### 6.2 自动保护

- 剩余比例低于 20%：黄色预警，标准策略保持不变；
- 低于 10%：自动降至保守档；
- 剩余为 0 或返回 `ERROR_VISIT_MAX`：暂停新的卖家精灵阶段，不进行无意义重试；
- 连续限流、超时或上游错误达到阈值：只降低对应连接器并发；
- 状态恢复后不自动升档，等待最高管理员确认；
- 暂停卖家精灵时，其他不依赖卖家精灵的阶段可以继续；依赖阶段明确显示“等待卖家精灵额度”。

## 7. 权限与界面

### 7.1 最高管理员

`admin@example.com` 可：

- 查看全部额度、速率、队列和错误信息；
- 手动刷新额度；
- 选择保守、标准或高速档；
- 修改允许范围内的高级参数；
- 配置官方未返回的套餐总次数；
- 暂停或恢复新任务；
- 查看策略修改审计。

### 7.2 其他管理员

其他 `admin` 角色可查看：

- 本月总额、已用、剩余和最近更新时间；
- 当前并发档位；
- 运行、排队和暂停任务数；
- 连接器预警和熔断状态。

其他管理员不可修改策略、额度总数或手动解除熔断。

### 7.3 普通用户

普通用户不查看公司套餐数字，只看到：

- 任务排队位置；
- 当前阶段和逐 ASIN 状态；
- “正常、排队、额度不足暂停、上游暂不可用”等业务文案；
- 已有任务的恢复入口。

## 8. 配置与审计

并发配置保存到 PostgreSQL，包含版本、修改人、修改时间和旧值/新值。系统启动时读取最近的有效配置；配置损坏时回退到保守档，而不是无限并发。

所有管理员操作均写 append-only 审计事件。审计元数据不得包含连接器密钥、数据库 URL、Cookie 或供应商原始响应。

参数必须有服务端硬上限。即使最高管理员也不能通过 UI 设置超过系统安全上限的值。

## 9. 错误处理和恢复

- API 接收任务后快速返回 `jobId` 和状态，不等待外部连接器完成。
- Worker 通过 PostgreSQL 原子 claim 与租约领取任务。
- Worker 进程退出后，租约到期的任务可由新 Worker 恢复。
- 页面刷新只恢复并轮询已有任务，不自动补发 POST。
- 单个连接器或单张图片失败写入逐 ASIN 缺口；允许安全完成的任务进入 `completed-with-gaps`。
- 全局队列、连接器队列、额度暂停和系统故障必须使用不同状态，不得统一显示为 96%。

## 10. 验收

### 10.1 无真实费用容量测试

使用 fake provider 模拟 20 个不同用户同时提交完整 3-ASIN 分析：

- 20 个请求的任务接收 p95 不超过 2 秒；
- 所有请求均获得任务 ID 或明确去重结果；
- 标准档同时运行任务不超过 4；
- 单用户同时运行任务不超过 1；
- 相同范围并发提交只产生一个任务和一个 Worker；
- 卖家精灵并发不超过 2，速率不超过每分钟 30；
- 图片全局并发不超过 2；
- 服务重启后 queued/running 状态可恢复；
- 页面刷新不新增 POST；
- 一个连接器故障不影响无关任务；
- 队列、额度、熔断和逐 ASIN 状态均正确显示。

### 10.2 真实连接器阶梯验证

真实连接器只按 1、2、4 个任务逐级验证。任何一级出现限流、额度异常或错误率上升即停止，不执行 20 个真实付费任务。

验证卖家精灵额度查询前后差值与系统记录的实际 HTTP 请求数；如果两者口径不同，保留双方数字及说明，不篡改记录以强行对齐。

## 11. 发布顺序

1. PostgreSQL 队列和策略存储；
2. 任务准入、去重、公平 claim；
3. 全局连接器与模型限流；
4. 卖家精灵额度采集和管理员只读界面；
5. 最高管理员策略控制和审计；
6. 20 用户 fake-provider 容量测试；
7. 真实连接器 1→2→4 阶梯验证；
8. 本地业务验收后再规划云服务器多 Worker 部署。

## 12. 回退

- 并发功能异常时，将策略切换为保守档并暂停新的完整任务；
- 不删除 queued/running 任务或历史报告；
- 不回退 PostgreSQL migration；通过禁用新调度功能回退行为；
- 不恢复旧 3000 启动链；
- 回退后现有任务仍可查询，管理员可逐项恢复。
