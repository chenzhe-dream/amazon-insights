# DingTalk OAuth Fresh Consent Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Force a fresh DingTalk browser OAuth consent so a newly enabled `Contact.User.Read` permission can be included in the user access token.

**Architecture:** Keep the current OAuth callback, `scope=openid`, identity exchange, account binding, and role rules unchanged. Add only `prompt=consent` to the authorization URL generated by `DingTalkAuthenticationService.startOAuth`, with a focused regression assertion covering all security-sensitive query parameters.

**Tech Stack:** TypeScript, Node.js URL API, `node:test`, `tsx`, ESLint, Vinext production build.

## Global Constraints

- Do not change DingTalk callback handling, workbench JSAPI login, provider token exchange, account provisioning, or role assignment.
- Do not log or expose AppSecret, authorization codes, access tokens, cookies, or complete provider response bodies.
- Preserve `scope=openid`, the exact configured callback URL, and the generated one-time OAuth state.
- Treat automated verification as proof of URL construction only; real DingTalk authorization still requires one manual retry.
