# Sorftime 与卖家精灵调用优化方案 V1

> 执行方式：按 executing-plans 顺序实施；本侧聊不使用子代理。本文件只确定方案，不代表已实现、已启用缓存或已发布。

**目标：** 在保留现有分析模块、有效数据覆盖和来源可追溯性的前提下，减少重复收费业务调用，并用任务账本和供应商余额分别验证请求节省与扣点节省。

**架构：** 优先扩展现有共享源数据缓存与事件账本，所有消费者复用同一供应商响应；模块结果仍分别绑定组织、项目、站点和任务。第一期限定同一任务，第二期才允许同一组织、同一凭据范围内的跨任务复用。

**技术栈：** Node.js/TypeScript、现有 MCP 客户端、PostgreSQL 源缓存与锁、任务编排器、现有回归测试。

## 2. 方案选择与边界

- 采用“同任务复用 → 跨任务缓存”两期实施，先验证较小范围的数据一致性。
- 暂不一次开启全部共享缓存：现有强制刷新、任务来源与错误分类需要先通过验证。
- 暂不减少评论、趋势、FBA、Listing 等模块，也不自动用另一供应商的相似字段替换现有数据。
- 连接复用作为后续速度优化项，单独统计；不将减少握手次数宣传为节省计费点数。
- SIF、图片模型和翻译模型本轮不改；共享代码变更仍需保证其回归通过。
- 第一、二期都先在独立候选工作区、数据目录和数据库验证。不得占用主线程正在使用的 33900/33901，也不改 32900/32901；新候选端口在执行前检查空闲后确定。
- 本轮仅落方案。优化实现与候选验收完成前，31900/31901 的配置和采集链路保持现状；后续发布沿用受管发布、空闲检查和可回滚流程。

## 3. 第一期：同一任务内复用

### 3.1 统一一次采集、多模块使用

- 商品详情由同一个数据源入口提供，评论数量、FBA、类目、变体、Listing、价格策略各自解析所需字段。
- 销量趋势已取得的 Price 响应供价格策略使用；保留原始采集时间和指标类型。
- 不同 CLI 子进程通过已有 PostgreSQL 源缓存和锁共享结果；不能只用单进程 Map。
- 同时请求相同数据时，只允许一个正常请求发往供应商，其余等待并复用；等待取消、超时不污染有效缓存。
- 同一任务默认有效复用窗口为 60 分钟；超过窗口按数据时效重新读取。恢复任务不能无限沿用旧数据。
- 缓存键至少包含：供应商、端点、组织、凭据范围、完整规范化参数、任务 ID 和刷新批次。参数包含站点、ASIN、页码、趋势类型、筛选条件、返回字段；不能使用省略参数的现有统计逻辑键作为去重依据。
- 原始响应可复用，但解析后的模块输出继续独立绑定当前项目和任务；不得借缓存绕过授权或混入其他站点报告。

### 3.2 卖家精灵详情合并

- 先用已有响应样本确认完整详情是否包含 badge、LQS、EBC、视频标记等字段。
- 若包含，Listing 从该详情解析；若不包含，验证供应商是否支持一次请求取得底库与 Listing 所需字段的并集。
- 字段集合不同只有在“已有响应覆盖所需字段”被明确证明后才可复用；无覆盖证明时保留补充调用。
- 不预先承诺减少 5 次收费调用，实际收益由字段覆盖与业务调用账本确定。

### 3.3 刷新与失败语义

- 普通分析：复用当前任务内有效响应。
- 强制刷新：开始一个新刷新批次，绕过旧批次；同一新批次内仍可复用，不能让每个模块都重新强刷一次。
- 补抓缺口：只补缺失或失败的 ASIN/模块；已有效的数据和图片不重复采集。
- 明确“上游无数据”的成功响应可以短期复用，默认 15 分钟；仍显示缺口，不写成零、不标记为完整数据。
- 网络失败、鉴权失败、限流与额度不足不进入成功缓存；沿用有上限的重试与熔断，不自动扩大重试次数。
- 部分成功只保留经验证的部分与来源，不能将缺字段的响应标记成所有模块已完成。

## 4. 第二期：跨任务缓存

第一期验收后，再在同组织、同凭据、同站点与完整参数匹配范围内灰度开启；以下为建议初始 TTL，可根据供应商更新频率调节。

| 数据 | 初始有效期 |
| --- | --- |
| 商品详情、FBA、变体结构 | 6 小时 |
| 历史销量/价格/BSR、类目趋势 | 24 小时 |
| 商品文案、图片链接 | 7 天 |
| 评论样本、评论摘要 | 24 小时 |
| 上游明确无数据 | 15 分钟 |

- 复用时展示真实采集时间，不把旧响应改成刚采集。
- 保留强制刷新入口，避免将未更新缓存误认为实时数据。
- 同一错误重复点击不立即产生无限新调用；人工强制刷新仍受限流和额度保护。
- 第二次同参数任务在 TTL 内，对缓存覆盖的业务请求目标为零外发；协议探测、未覆盖工具、失败重试单独解释。

## 5. 统一计量与验收账本

每个任务分别记录以下口径：

1. 业务读取需求次数：各模块提出了多少次读取。
2. 任务内命中、跨任务命中、并发等待后命中：明确节省来源，避免重复相加。
3. 实际 tools/call 请求尝试及重试：按工具、参数身份、ASIN/类目、阶段统计。
4. initialize、通知、tools/list、关闭等协议请求：单独计数。
5. 估算点数：记录计价规则版本，未知工具保持未知；检查 Rank/BsrRank 等实际参数与计价映射是否一致。
6. 实际扣点：仅在供应商支持余额或账单核对时确认。前后快照若混入其他任务或外部账号使用，不能直接归因本任务。

无供应商账单时，结果明确写“请求减少 N 次，估算点数 M，实际扣点未确认”，不得将请求数直接改名为额度。
