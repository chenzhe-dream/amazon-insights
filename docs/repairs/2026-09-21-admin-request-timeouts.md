# 人员管理等待与保存结果核对

## 已确认的范围

用户批准把人员读取与权限保存等待延长至 60 秒。此次修改只覆盖会话读取、人员状态、使用统计/人员搜索、模块显示配置及新用户默认模块配置。其他业务的超时策略不变。

代理和后端原来各自有 10 秒限制；现在白名单路由的代理总等待和后端 handlerTimeout 都改为 60 秒。代理预算包含响应体读取。会话读取为人员管理的前置步骤，因此同样使用 60 秒；登录提交等接口不在白名单中。

个人及批量模块保存遇到 504、502、网络断开或成功响应损坏时，仅执行一次只读核对。核对最多等待 5 秒，必须匹配用户 ID、递增的版本、完整模块集合和显式授权值。匹配时确认当前配置，不匹配或无法读取时提示“保存结果尚未确认”，不会自动再次 PUT。批量仅修改显示范围时，核对不要求也不修改统计授权。

## 调查证据与限制

- 正式数据库只读抽样：人员列表约 4–8ms、模块配置列表约 3–9ms；这只是当时的查询测量，不是其他电脑的完整加载耗时。
- 首次通过文件列表看到新日志长度为 0；后续直接读取获得请求记录，隔离子进程/孙进程测试也未复现日志丢失。因此保留现有启动器，撤回“日志未落盘”的确定性判断。
- 新日志显示 2026-09-21 17:43:25 起的一次人员接口耗时约 3350ms；17:42:59.850 收到的模块配置 PUT 缺少请求完成记录，对应时段存在 17:43:00.342 的数据库提交记录。不能将提交成功等同于浏览器收到响应。
- 现在为管理请求记录关联 ID、路由模板、代理等待响应头/读取响应体/总耗时，以及后端共享鉴权后、响应准备好、发送完成或连接关闭的时间点。新增诊断不记录账号、实际 userId、查询参数、cookie、token 或请求体。
- 这些耗时用于区分处理与传输阶段，不能代替 SQL 专项测量。延长等待不能证明人员加载已经变快，历史慢点仍需下一次真实请求验证。

## 验证与发布状态

- 8 个定向测试文件最终回归通过 64 项，包括代理响应体超时、权限隔离、授权撤销、PostgreSQL 真实路由、连接中断日志及 5 秒核对上限测试。
- 定向 ESLint、TypeScript 与 OpenSpec 严格校验通过。
- 本轮未重启或发布正式服务。正式生效需要发布前后端并重启后端；现有发布活动任务与版本检查继续保留。
