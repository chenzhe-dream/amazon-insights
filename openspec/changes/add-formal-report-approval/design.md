## Context

当前系统已经保存不可变 AnalysisReport 版本，并通过人工评分与自动门槛控制智能体实现能否成为主结果。这些机制回答“智能体实现是否达到质量标准”，不回答“某位有权限的业务审核人是否批准发布这一份报告”。正式报告审批需要独立身份、状态和审计边界。

## Goals / Non-Goals

**Goals:**

- 把审批精确绑定到 `reportId`、`version`、`contentDigest`。
- 使用闭合状态机和不可变事件，支持提交、批准、拒绝、撤销与新版本失效。
- 让审批权限和报告作者、模型质量评分、智能体发布开关彼此独立。
- 保留每次决定的操作者、时间、原因与前后状态。

**Non-Goals:**

- 本设计不实现 API、UI、数据库迁移、通知或电子签名。
- 不改变报告内容，不在审批时重新运行模型。
- 不把正式报告审批扩展为产品立项或跨部门法务/财务审批。
- 不从人工六维评分或 9.4 release decision 自动推导报告批准。

## Decisions

### 1. 审批主体是不可变报告版本

审批身份由 `organizationId + reportId + version + contentDigest` 组成。系统在接受任何状态转换前重新读取报告并验证四项完全匹配。内容不同的新版本是新的审批主体，不能继承旧版本状态。

### 2. 使用闭合状态机

状态为 `not-submitted`、`pending-review`、`approved`、`rejected`、`revoked` 和 `superseded`。

- `not-submitted → pending-review`：有权限的提交者提交审核。
- `pending-review → approved | rejected`：有权限且满足职责分离的审核人决定。
- `approved → revoked`：授权人员因新风险撤销，必须填写原因。
- 新报告版本产生后，旧版本的 `pending-review` 或 `approved` 可追加 `superseded` 事件，但历史不删除。
- 其他转换全部拒绝；重试同一幂等命令不得追加冲突事件。

### 3. 审批事件不可变追加

每个事件保存事件 ID、组织、报告身份、前后状态、动作、操作者、角色、原因、关联请求和时间。当前状态由严格解析的最新有效事件派生；损坏、跨组织或读取失败时 fail closed 为未批准。

### 4. 质量评分与正式审批分离

人工六维评分评估智能体输出质量；9.4 release decision 决定 agent 是否可成为某模块主结果；正式审批决定特定报告版本是否经过业务审核。三者不得互相替代，也不得共用含义模糊的 `approved` 记录。

### 5. 批准不代表产品立项

正式报告批准只允许报告进入未来定义的受控发布/导出范围。成本、利润、专利、合规、预算和供应链仍使用各自门槛；页面和导出必须持续显示该边界。

## Concurrency and Failure Handling

状态转换使用事务内比较当前版本的乐观并发或等价原子条件。重复请求使用幂等键返回原事件；基于旧状态的竞争请求失败且不产生事件。报告缺失、摘要不匹配、角色不足、职责分离失败、审计读取异常或事件损坏均不得得到 approved 结果。

## Deferred Adoption

该状态机、权限矩阵、存储和界面需要在后续实现 change 中共同验收。当前 AnalysisReport 仍作为带边界的 `analysis-result` 展示，不具有正式审批状态。
