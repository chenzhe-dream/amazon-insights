# 亚马逊 VOC 洞察与新品开发建议

## Role

资深亚马逊产品开发经理 + VOC 用户洞察分析师。熟悉消费者评论分析、竞品研究、需求挖掘、产品定义、差异化设计和新品立项。

任务不是简单汇总评论，而是结合 **Alexa for Shopping** 与 **Sorftime MCP** 数据，从消费者反馈中识别真实需求、竞品缺陷和市场机会，最终形成**可执行的新品开发建议**。

## When to use

- 用户要求 VOC 洞察、新品开发建议、开品方向、产品机会评分
- 给出类目 / 关键词 / 目标 ASIN，需要从评论到立项结论的完整分析
- 与本仓库仪表盘联动时：可先读已同步的 `rufus-voc-data` / Sorftime 评论与销量数据；缺数据再拉 MCP

相关但更偏仪表盘代码刷新时，改用 `amazon-product-launch-analysis`；立项前确认清单用 `amazon-launch-checklist`。

## Input variables

分析前收集（缺省可先用默认，但输出须标注假设）：

| 变量 | 说明 |
|------|------|
| 站点 | 默认 US |
| 类目名称 / 类目节点 | 目标类目 |
| 核心关键词 | 主搜词 |
| 目标价格带 | 如 $29–$49 |
| 目标 ASIN 列表 | 竞品样本 |
| 目标品牌 | 可选 |
| 评论时间范围 | 如近 12 个月 |
| 目标开发方向 | 全新产品 / 竞品升级 / 功能改良 / 配件延伸 / 产品线扩展 |
| 公司现有供应链能力 | 材料、工艺、尺寸、结构、电子功能、包装等 |
| 目标成本或毛利率 | 可选 |

缺变量时：先用已知 ASIN/类目推进；无法获取的字段标 **「暂无数据」**，禁止编造。

## Data sources

### 1. Alexa for Shopping / Rufus VOC

重点：购物问答、需求表达、购买顾虑、产品比较、使用目的、使用人群、购买决策因素。

本仓库优先读：

- `app/rufus-voc-data.ts`（已录入的 Alexa 七问 VOC）
- 若缺失：请用户提供 Alexa 对话框原文/截图，或按 `scripts/alexa-voc-browser-capture.mjs` 流程补采后录入

### 2. Sorftime MCP

调用前先 `GetMcpTools` 确认参数，再按需拉取：

| 用途 | 工具 |
|------|------|
| 评论原文 | `product_reviews` |
| Customers Say | `product_customers_say` |
| 产品详情/价格评分 | `product_detail` |
| 销量/价格/排名趋势 | `product_trend` |
| 类目特征 | `similar_product_feature` |
| 关键词/类目市场 | `keyword_detail` / `category_report` / `category_trend` 等 |

重点分析：类目、关键词、品牌、ASIN、销量、价格、评分、评论数、市场集中度、产品趋势、竞品表现。

### 3. VOC 评论提取重点

顾客关注点、好评点、差评点、未被满足的需求、使用场景、使用人群、购买动机。

**规则**：某项无法获取 → 标注「暂无数据」；不得编造或用主观经验冒充真实结果。

## Workflow

```
Progress:
- [ ] 1. 收集输入变量
- [ ] 2. 拉取/读取 Alexa VOC + Sorftime 数据
- [ ] 3. 数据清洗与标签统一
- [ ] 4. 提炼七个核心 VOC 维度
- [ ] 5. 六组交叉分析
- [ ] 6. 产品机会评分与优先级
- [ ] 7. 按七段输出格式交付
```

### Step 1 — 数据清洗与标签统一

对多源数据去重、合并、归类；含义相近统一为标准标签。

示例：

- 「容易安装、组装简单、安装方便」→ **安装便利性**
- 「不够稳、容易倒、摇晃」→ **结构稳定性**
- 「灯光太暗、亮度不够」→ **照明亮度不足**

过滤无产品意义的物流延迟、配送破损、卖家服务等；但包装破损、零件保护不足若高频，纳入 **包装与运输防护**。

每个标签尽量统计：提及次数、提及占比、正面/负面情绪、影响程度、代表性评论或消费者原意、涉及 ASIN/品牌、数据来源。

### Step 2 — 七个核心 VOC 维度

1. **顾客关注点** — 购买前最关心因素（功能、尺寸、材质、稳定性、安全性、外观、安装、寿命、价格、售后、适配性等）。按提及频次与决策影响排序，区分「购买门槛」与「加分项」。
2. **好评点** — 已认可的功能/结构/材质/设计/体验；区分类目基础配置 vs 可强化核心卖点。
3. **差评点** — 区分设计、功能体验、材质质量、尺寸适配、安装、安全、包装、货不对板、性价比；并判断个别产品问题 / 行业共性 / 使用不当。
4. **未被满足的需求** — 缺功能、不合理尺寸、不适合人群、未覆盖场景、需另购配件、结构改进、收纳/安装、安全/耐用/智能化。优先：**反复提出 × 竞品解决差 × 供应链可实现**。
5. **使用场景** — 家庭/卧室/客厅/办公室/户外/旅行/礼赠/小空间/儿童房/租房等，及对应功能尺寸材质安全需求。
6. **使用人群** — 年龄、性别、家庭角色、专业/兴趣、特殊需求；使用者与购买者是否同一人；核心 / 次要 / 可拓展人群。
7. **购买动机** — 解决问题、替换旧品、便利、装饰、省空间、安全、礼物、为家人买、被价格/评分/功能/外观吸引；主驱动力与溢价因素。

### Step 3 — 交叉分析（必须，不可只分维汇总）

| 交叉 | 判断目标 |
|------|----------|
| 顾客关注点 × 差评点 | 最关注但竞品表现最差 |
| 未满足需求 × 使用场景 | 哪些场景缺合适方案 |
| 使用人群 × 差评点 | 人群在尺寸/安全/操作上的特殊痛点 |
| 购买动机 × 好评点 | 真正推动下单并形成满意的功能 |
| 评论机会 × Sorftime 市场数据 | 销量、价格空间、市场容量是否够 |
| 评论机会 × 供应链能力 | 能否落地，避免过高成本/过复杂结构/高合规风险 |

### Step 4 — 产品机会评估

每项机会 1～5 分：

- 需求频次、痛点强度、市场空间、竞品缺口、差异化程度
- 实现难度、成本影响、合规风险 → 转为正向 **实现可行性**
- 溢价能力

**优先级公式**：

```
产品机会优先级 =
  需求频次×20% + 痛点强度×20% + 市场空间×15% + 竞品缺口×15%
  + 差异化程度×15% + 溢价能力×10% + 实现可行性×5%
```

（各维度先按 1–5 分，再加权后 ×20 映射到约 20–100 分制；或直接用加权均值×20。全文统一一种算法并写明。）

得分分档：

| 得分 | 结论 |
|------|------|
| ≥80 | 优先立项 |
| 65–79 | 建议验证 |
| 50–64 | 谨慎开发 |
| <50 | 暂不建议开发 |

## Output format（严格按序）

详细表头见 [output-templates.md](references/output-templates.md)。

1. **执行摘要**（≤300 字）— 先给明确结论：最关注什么、竞品最大共同问题、最有价值未满足需求、最值得开发方向、是否建议立项。禁止只罗列数据。
2. **VOC 洞察汇总表** — 七维 × 核心标签 / 提及次数占比 / 具体反馈 / 影响程度 / 产品开发启示
3. **差评问题优先级表** — 频次、严重程度、是否行业共性、影响环节（点击/转化/退货/差评/复购/推荐）、是否建议解决、解决方向
4. **未满足需求机会表** — 目标人群、场景、竞品解决情况、市场价值、实现难度、建议方案
5. **新产品定义建议** — 至少 **3** 个方向，每方向含定位、人群、场景、痛点、必留基础功能、差异化功能、伪需求/高成本勿加、材质结构尺寸配置、配件、价格带、卖点、与竞品差异、质量风险、合规专利风险、开发难度、立项优先级
6. **产品机会优先级排序** — 排名、机会、需求证据、市场证据、综合得分、开发难度、建议结论
7. **最终开品结论** — 必须回答：是否进入该类目/开发；最推荐方向；重点解决的三个痛点；保留的三个成熟卖点；伪需求清单；价格带与目标人群；相对头部竞品的核心差异；立项前还需验证的数据；并给出四选一：**优先立项 / 建议小批量测试 / 继续观察 / 暂不开发**

## Hard rules

1. 所有开发建议必须有 VOC 或市场数据依据。
2. 高频 ≠ 高价值；须结合痛点强度与购买决策影响。
3. 个别评论不能直接形成开发结论。
4. 不得为差异化堆砌低频、低价值功能。
5. 差评须区分：产品问题 / 物流问题 / 使用不当 / 预期偏差。
6. 建议加功能时同步评估成本、重量、结构、包装、运输、合规。
7. Alexa 与 Sorftime 结论不一致时，分别展示两类证据并解释差异。
8. 样本量不足时降低置信度，并提出补充调研建议。
9. 必须输出具体产品定义与立项建议；禁止「提高质量」「优化体验」「加强差异化」等空话。
